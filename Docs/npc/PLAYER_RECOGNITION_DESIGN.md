# NPC 관찰 반응 시스템 (Reactive Recognition) — 설계
_디자인 확정: 2026-07-22_

> **한 줄**: NPC가 플레이어의 *관찰 가능한 상태*(1호 신호 = 몬스터 전리품 보유)를 보고 **먼저 반응**해,
> 그 NPC의 **신뢰(Trust)** 를 단계적으로 쌓고 대사·보상으로 되돌려준다. NPC의 요구도, 플레이어의 수락도 없다.
>
> **원 목표**: NPC가 "마을 밖 몬스터가 위협적이라 무섭다"고 말할 때, 플레이어가 (직접 잡았든 상점에서 샀든)
> 몬스터 전리품을 지니고 있으면 NPC가 그걸 알아보고 대화·보상이 달라진다.
>
> **상태**: 🟦 설계 확정 — 미구현. 트랙 A(몬스터·전리품 콘텐츠) 선행 의존.

## 디자인 (durable — 구현 후에도 유효)

### 결정 사항

- **정체성 = 요구가 아니라 반응.** NPC가 플레이어의 상태를 관찰하고 *먼저 반응*하는 시스템. 목표 제시·수락·부탁이 없다.
  - 이유: 개인 소망(QUEST)은 NPC→플레이어 **요구**("이걸 해줘"), 본 시스템은 플레이어→NPC **관찰·반응**("자네 그런 걸 가졌군"). 이 **방향성 차이**가 두 시스템을 가르는 본질이다.
  - 기각한 대안: **현상금/의뢰(Bounty) 모델** — NPC가 "몬스터 잡아와"를 목표로 제시하고 플레이어가 수행. 기각: (a) 거래·의뢰 뉘앙스가 관계 몰입 프레이밍과 안 맞고, (b) "플레이어가 몬스터를 꼭 잡을 필요는 없다"(전리품을 상점·탈취·습득 등 **어떤 경로로든** 보유해도 됨)는 핵심과 충돌.

- **위협도 내부 계산(Phase F)을 하지 않는다.** `VillageData.ThreatLevel` 실데이터 없이 관찰 증거(전리품 보유)로 대체.
  - 이유: 몰입감 — 내부 수치보다 "NPC가 눈에 보이는 증거를 보고 반응"이 생생. 또한 ThreatLevel 계산 시스템은 설계 문서조차 없는 미개척 영역이라 우회로 회피.
  - 기각한 대안: 근접 몬스터 수/난이도로 ThreatLevel 계산(SPIKE §D2가 예고). 기각: 위 이유 + 전리품을 사올 수도 있어 "세계 위협도"와 "플레이어 신뢰"는 별개 개념.

- **출력 = 기존 `PlayerRelation.Trust` 축 재사용.** 인지가 Trust를 올린다. 새 상태를 만들지 않는다.
  - 이유: 관계 4축(Affinity/Trust/Fear/Intimacy) 중 Trust는 `TrustCap` 불변식까지 있는데 **현재 아무것도 올리지 않는 빈 축**이다 — 딱 맞는 용처. 대화/선물이 Affinity·Intimacy를 올리듯, 본 시스템이 Trust를 담당.

- **대사 변화 = per-NPC 신뢰 (village-wide 아님).** "자네 같은 사람이 있어 마음이 놓이오" 식 *그 NPC의 플레이어 신뢰* 대사.
  - 이유: 전리품을 사올 수도 있으니 "세상이 안전해졌다"는 세계 상태 추론이 논리적으로 안 맞는다. "**자네는** 밖을 감당할 사람"이라는 플레이어 인식이 정합적.
  - 기각한 대안: **마을별 안전감 카운터(village-wide)** — 세션 중간에 잠정 채택했다가 폐기. 기각: 관찰 증거가 세계 상태를 보장하지 않아 위 논리와 모순 + 초기엔 per-NPC로 충분.

- **일반 프레임워크 (신호 확장 계층).** NPC가 관찰하는 "신호(player signal)"를 확장 가능한 계층으로 설계. 몬스터 전리품 보유 = **1호 신호**, 이후 장비·재산·업적·외형 등은 등록만으로 추가.
  - 이유: "플레이어를 보고 반응"이라는 취지가 전리품 하나에 국한되지 않는다. 골격을 일반화하면 신호 추가 비용이 낮다.
  - 단, 실제 구현은 1호 신호(전리품)부터 — 프레임워크는 일반, 첫 구현은 좁게.

- **신뢰 단계적 상승 (staged).** 전리품 종류·수가 늘수록 임계값마다 인지+보상. "반복 가능"을 관계 심화로 재해석.
  - 이유: 증거당 1회보다 지속적 상호작용이 관계 몰입에 맞는다.

- **보유(디폴트) + 전달(variant).** 보유형 = 비소모 관찰(인벤토리에 있으면 인지). 전달형 = 드물게 NPC가 인지 후 "그거 내게 넘겨주면…"이라 *선택적으로 제안*(소모).
  - 이유: 상호작용 다양성.
  - 주의: 전달 variant는 "요구 없음" 원칙과 긴장 관계. **인지 후 NPC가 먼저 건네는 선택적 제안**으로만 프레이밍(선퀘스트 아님). 정확한 경계는 열린 질문.

- **개인 소망(QUEST)과 별도 시스템 + 하부 배관 공유.** 상위 타입·개념·UI·티어·생성은 분리, 하부는 공유.
  - 공유: **인벤토리 관찰/감지 계층** + **세이브 패턴**(`WorldData` + 매니저).
  - 이유: 방향성 반대(요구 vs 반응)라 개념 분리 필수. 그러나 감지·저장 배관 이중 구현은 낭비.

- **아키텍처 배치 = 이벤트성 평가 + 관계 세이브 상태 (System 아님).** 인지 평가는 매 틱이 아니라 **Talk 상호작용 시점**에 한 번 돈다 → `IUpdateSystem`/`System_*`로 만들지 않고, Talk 처리 경로에서 호출되는 **무상태 평가 로직**으로 둔다. 관찰 대상(인벤토리)도 Talk 때 스냅샷으로 읽는다.
  - 이유: 프로젝트 로직 배치 규칙 — 매 틱 도는 게임플레이가 아니면 System이 아니고, 지속 상태는 소유자(세이브)가 있어야 한다.

- **인지 상태 = 신호별 "마지막 인지 단계"를 관계 세이브에 합류.** 재보상·재상승을 막기 위해 (npc, 신호)별 마지막 인지 단계를 저장하고, `PlayerRelation` 세이브 경로에 얹는다.
  - 이유: Trust 값만으로는 "이미 이 단계 보상을 줬는지"를 못 가린다 — Trust는 여러 신호·상호작용의 합이라 단조 증가만으로 단계 판정이 안 됨.
  - 데이터 모양(`PlayerRelation` 필드 vs 병렬 구조)은 구현 시 확정 → 열린 질문.

### 제약 · 전제

- **트랙 A 의존 (식별 인터페이스가 아직 없음).** 본 시스템은 "이 `ItemData`가 몬스터 전리품인가 / 어느 위협 범주인가"를 묻는 식별 인터페이스에 의존한다. **현재 이 인터페이스는 없다** — `ItemTable`에 `DropRate`/`DropLevel`이 있으나 이는 드랍 확률·레벨일 뿐 "몬스터가 떨군 것"을 자원 노드·상자 드랍과 구분하지 못한다. 트랙 A가 식별 수단(신규 `ItemTable` 태그/`ItemType` 값 vs 몬스터→드랍 매핑 테이블)과 콘텐츠(몬스터·전리품 확충)를 함께 정한다. 현재 몬스터·아이템 수가 적은 것도 트랙 A에서 해소. 본 문서는 결과 인터페이스에 **의존만** 한다.
- **관계 데이터는 ECS가 아니다.** `PlayerRelation`은 `NpcManager` + `WorldData` 소유. 본 시스템도 같은 패턴(ECS 컴포넌트 안 만듦).
- **`PlayerRelation` 4축은 이미 구현되어 있다**(코드 기준: `NpcManager`의 Get/Set/Modify + 세이브). ⚠️ `Wiki/npc.md`는 이를 "미구현"으로 표기 — 드리프트이므로 위키를 신뢰하지 말고 코드를 기준으로 볼 것.
- **대사 파이프라인은 신설하지 않는다.** 기존 내러티브 스파이크(대화 토픽 선택 + LLM 서술 + 캐시)의 `ClearThreat` 토픽을 Trust 티어로 게이트해 재사용한다.

### 구조 의도

- **왜 별도 시스템인가** — 요구(QUEST) vs 반응(본 시스템)의 방향성 차이. 한 타입에 섞으면 "NPC가 시키는 것"과 "NPC가 알아봐 주는 것"이 개념적으로 뒤엉킨다.
- **왜 Trust 축인가** — 관계 4축 중 유일하게 비어 있고 의미가 정확히 맞는다. 신뢰는 "관찰된 행실"에서 쌓이는 것이라 관찰 반응의 자연스러운 출력.
- **신호 계층을 일반화하는 경계** — 감지 대상(무엇을 관찰하나)은 데이터/훅으로 확장, 반응 로직(Trust 상승 → 대사 게이트 → 보상)은 신호 종류와 무관하게 공통.
- **QUEST와 공유하는 경계** — "인벤토리에 무엇이 있나"를 읽는 감지 계층과 영속화 패턴까지만 공유. 그 위(요구냐 반응이냐, 대상 어휘, 생성)는 분리.

### 열린 질문

- [ ] 전달 variant의 정확한 프레이밍 경계 — "요구"가 되지 않으면서 아이템 소모를 유도하는 지점.
- [ ] Trust 단계별 임계값·보상 수치 (밸런스 후순위 — 골격만 먼저).
- [ ] 인지 단계 상태의 데이터 모양 — `PlayerRelation`에 필드 추가 vs (npcId, signalId)→단계 병렬 맵. 신호가 늘 때의 확장성 고려.
- [ ] 관찰 시점이 Talk 상호작용만으로 충분한지 (근처에 있을 때 수동 인지 등은 후순위).
- [ ] 1호(몬스터 전리품) 이후 신호 확장 목록(장비·재산·업적·외형…)의 우선순위.
- [ ] 반응성 보상의 성격 — goodwill 제스처(선물/소액 골드)의 구체 범위.
- [ ] 트랙 A의 전리품 식별 방식(태그 vs 드랍테이블) — 트랙 A 문서에서 확정.

## 구현 계획 (2026-07-22 기준 — 완료 시 이 블록 전체 삭제)

> 범위 = 트랙 B(본 시스템), 1호 신호(몬스터 전리품)까지. 트랙 A(몬스터·전리품 확충 + 식별 인터페이스)는 **선행 별도 작업**이며 이 계획의 전제다.

### 코드 앵커 (구현 시작점 — 개념 → 현재 위치)

라인 번호가 아니라 개념·심볼로 가리킨다(리팩터 견딤).

| 개념 | 현재 위치 | 비고 |
|------|----------|------|
| 플레이어 인벤토리 | `PlayerManager` → `AR.s.Player.Inventory.Items` (`List<ItemData?>`, 슬롯 기반) | `ItemData.Table`(=`ItemTable`)에 `ItemType`/`Category`/`DropRate`/`DropLevel`/`BasePrice`. **몬스터 전리품 식별 필드는 없음**(트랙 A) |
| Talk 상호작용 경로 | `InteractionHelper.Resolve(npcId, Talk)` (무상태 판정) ← `UINpcInspect`의 대화 클릭 핸들러 | 인지 평가를 이 경로, **대화 생성 前**에 삽입 |
| 관계·Trust | `NpcManager.GetPlayerRelation`/`ModifyPlayerRelation(npcId, dAff, dTrust, dFear, dIntimacy)`; `PlayerRelation{Affinity,Trust,Fear,Intimacy,TrustCap}` | Trust 델타는 현재 어디서도 안 씀 — 본 시스템이 첫 사용처 |
| 관계 세이브 | `NpcManager.SavePlayerRelations`/`LoadPlayerRelations`, `PlayerNpcRelationEntry`, `WorldData.PlayerNpcRelationList` | 인지 단계 상태를 여기 합류 |
| 대화 토픽/생성/캐시 | `Scripts/Npc/Narrative/` — `DialogueTopicSelector`(`ClearThreat`는 `AddNeeds`), `NpcNarrativeService.GetDialogueAsync`, `NpcNarrativeRuntime`(캐시 + `InvalidateDialogues`) | 캐시 키 = (npcId, tier, topicType, CacheVariant) |
| 현재 위협 시드 | `ThreatSeed` 구조 + `UINpcInspect`에서 **하드코딩**(`NearbyMonsters=true`) | 이 하드코딩을 인지 결과 기반으로 교체 |
| 현재 티어 산출 | `UINpcInspect.GetAffinityTier(affinity)` → `AffinityTier` | ClearThreat의 Trust 게이트는 별도 축 → Trust 값을 토픽 선택에 전달 필요 |

### 단계

- [ ] **감지 계층** — Talk 시점에 `AR.s.Player.Inventory.Items`를 스냅샷으로 읽어 "몬스터 전리품 신호"를 산출. 트랙 A 식별 인터페이스 사용. 신호를 확장 가능한 추상(감지기 = 플레이어 상태 → 신호 강도)으로 두고 1호(전리품)만 등록.
- [ ] **인지 평가(무상태) + Trust 상승** — 신호 강도(전리품 종류·수)를 단계 임계값에 매핑. 해당 NPC의 마지막 인지 단계보다 높을 때만 `ModifyPlayerRelation`으로 Trust↑(TrustCap 준수)하고 마지막 인지 단계 갱신. Talk 처리 경로에서 대화 생성 前에 호출.
- [ ] **인지 상태 영속화** — (npc, 신호)별 마지막 인지 단계를 관계 세이브(`PlayerNpcRelationEntry`)에 합류. 구 세이브 마이그레이션 가드(없으면 0).
- [ ] **대사 게이트** — `DialogueTopicSelector`의 `ClearThreat`를 Trust 단계로 분기(하소연 → 안심·인정 BaseLine). `CacheVariant`에 Trust 단계를 실어 단계 변화 시 자동으로 새 대사. Trust를 토픽 선택 입력으로 전달. `ThreatSeed` 하드코딩 제거·인지 결과 연동.
- [ ] **반응성 보상** — Trust 마일스톤에서 goodwill 보상(소액 골드/아이템). 요구·수락 없이 NPC가 먼저 건네는 형태.
- [ ] **전달 variant** — 드물게, 인지 후 NPC가 "그거 내게 넘겨주면…" 선택적 제안(소모형). "요구"가 되지 않는 프레이밍 확정 후 착수.
