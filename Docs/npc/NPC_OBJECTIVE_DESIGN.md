# NPC 단기 목표 설계 — 사건과 상황이 며칠짜리 목표가 되게 (Objective)

> 작성일: 2026-10-16 (첫 이름 "다짐", 문서 `NPC_VOW_DESIGN.md`)
>
> 개정(2026-10-18, 사용자 결정): "다짐"이라는 특수 기능을 공용 **단기 목표** 틀로 바꿨다. 설욕은 이 틀에 들어가는 목표 종류 하나가 된다. 함께 정한 것:
> - 이름은 **단기 목표**, 코드는 `NpcObjective`, 문서는 이 문서다. `Goal`은 길찾기 목적지(`PathfindingComponent.Goal`)와 대화 콘텐츠 진행 방식(`NarrativeGoalType`)에서 이미 쓰고 있어 쓰지 않는다.
> - NPC 한 명은 목표를 **1개**만 가지고, 우선순위가 더 높은 목표가 오면 밀어낸다.
> - **일상 목표**도 넣는다. 일상 목표는 활동 배율을 작게 두거나 아예 두지 않는다.
> - 기존 기능 중 1단계에서는 **소문 확인**(확인 원정)만 이 틀로 옮긴다.
> - "다짐"이 예약해 둔 번호를 이어받는다: 결정 D142~D152, `NpcDeedKind` 16·17, `NarrativeContentKind` 5, RNG salt 200~209.
>
> 개정(2026-10-18 두 번째, 사용자 결정):
> - 목표는 다음 활동의 **확률을 기울이기만** 한다. 실행 단계에 들어가도 원정을 바로 고르게 하는 안은 쓰지 않는다.
> - 이룸·꺾임이 아닌 이유로 칸에서 **빠진** 목표는 지우되, **칸이 빌 때 사건 기록(최근 14일)에서 다시 계산**해 조건이 맞으면 다시 세운다. 그보다 오래된 기록은 계산하지 않는다(§4.8).
> - 극적 목표의 기한과 준비 시간은 **사건 시각 기준**이다. 다시 계산해도 같은 값이 나오게 하기 위해서다.
> - 던전 원정 사망과 중상의 Deed에 **던전**을 남긴다. 시도 횟수는 계산할 수 없어 다시 생긴 목표는 0회부터 센다.
> - 원수 갚기는 같은 마을 관계자가 **각자 판정**하고, 관계가 가까울수록 확률이 높다. 같은 죽음을 여러 명이 쫓을 수 있다.
> - **마을 상한, 연쇄 깊이 상한, 같은 던전 부탁 제한은 두지 않는다.** 같은 대상을 노리는 목표 주인끼리는 파티 합류를 허용한다. 몰림은 진단으로 본다.
> - 장비 마련은 같은 종류의 새 계기에서 **더 좋은 매물이면 대상만 바꾼다.**
> - 죽은 NPC의 기록은 별도 작업인 **사망자 최소 기록**으로 줄인다([NPC_SIMULATION §5.2](NPC_SIMULATION_DESIGN.md)). 원수 갚기는 그 기록에 남는 사망 Deed(시각·던전)만 읽는다.
>
> 개정(2026-10-18 세 번째, 사용자 결정):
> - 정의 표는 구글 시트의 새 탭 `NpcObjective`로 둔다(D147).
> - 구현 전 빈도 확인 단계는 따로 두지 않는다. 확률은 시작값이므로 1단계 본체 진단에서 던전 원정의 중상·사망 수와 장비 마련 계기 수를 함께 센다.
> - 구현 순서는 단기 목표 1단계 → 사망자 최소 기록(별도 작업)이다.
>
> 상태: 🟨 1단계(소문 확인 이관·장비 마련·원수 갚기·설욕) 구현·진단 통과(2026-10-18), 실플레이 확인·커밋 대기 — 결과는 §12.1. 구조·규칙·정의 표(시트)는 사용자 결정으로 확정했다(§3). 수치(우선순위·확률·시간·배율)는 시작값이며 진단으로 맞춘다.
>
> **한 줄**: NPC가 겪은 사건이나 처한 상황이 며칠짜리 **단기 목표**가 되어 활동에 이유·대상·끝을 붙인다. 목표가 끝나면 그 결말이 다른 NPC의 계기가 될 수 있다.
>
> **책임**: 단기 목표의 공용 틀(목표 칸, 정의 표, 생성·다시 계산·단계·결말, 알림 지점)과 1단계 목표 종류(소문 확인, 장비 마련, 원수 갚기, 설욕)를 정의한다. 활동 판정(성공률·부상·사망·전리품·완료 확률)은 바꾸지 않는다.
>

## 1. 문제와 목표

### 1.1 지금 상태 (2026-10-18 코드 기준)

NPC에게 일어나는 사건은 이미 많다. 그런데 사건이 **기록으로만 남고 다음 행동을 거의 바꾸지 않는다.**

다음 활동은 Idle이 될 때마다 휴식·사냥·거래·던전 원정 중에서 점수 가중 랜덤으로 새로 고른다. 이전 사건이 주는 입력은 골드 부족·가방 가득·회복 직후·유망한 소문 네 가지뿐이다. [src: Assets/Scripts/Npc/NpcActivityResolver.cs `NpcActivityChoiceContext`, Assets/Scripts/Manager/NpcManager_Ambition.cs `BuildActivityChoiceContext`]

| 사건·상황 | 지금 남는 것 | 다음 행동에 주는 영향 |
|---|---|---|
| 동료·가족 사망 | 생존자의 사망 관계 기억·공동 활동 기억, 대화의 사별 화제 | 없음 |
| 원정 중상 | 중상 Deed(종류·시각), 마지막 부상 활동·던전(`LastWoundDungeonId`, 다음 부상 때 덮임) | 회복 직후 12시간 휴식 ×1.5 |
| 절도 발각 | 호감도 −40, 원한, 가족·친구 −10 (D102) | 같은 파티에 안 듦, 소문을 안 나눔 |
| 유망한 소문 보유 | 소문 목록 | 던전 원정 ×1.5, 그 던전으로 확인 원정 (D76) |
| 상점에서 비싼 업그레이드를 봄 | 없음 | 없음 |

공통 목표인 "강해지기"도 이야기를 끌고 가지 못한다. 추격과 역전 기조 때문에 NPC 전투력은 일부러 거의 평탄하게 만들었다(AMBITION §1.2·§10.1). 성격이 활동 빈도에 주는 영향도 ±20% 이내라(D40) 눈에 잘 띄지 않는다. 유망한 소문만 예외적으로 "어디로 갈지"를 정하는데, 이것은 사실상 이미 단기 목표다.

### 1.2 목표

1. **사슬**: 사건·상황 → 단기 목표 → 활동 변화 → 결말 → 다른 NPC의 계기.
2. **하나의 틀**: 소문 확인처럼 극적이지 않은 목표와 원수 갚기처럼 극적인 목표가 같은 부품을 쓴다. 새 목표는 대부분 정의 표의 행 하나로 더한다.
3. **성격이 반응을 고른다**: 같은 사건을 겪어도 성격에 따라 목표를 세우거나 묻어 둔다.
4. **플레이어가 알아볼 수 있다**: 검사 창과 대화에 드러난다. 원하면 끼어들 수 있지만, 끼어들지 않아도 목표는 끝난다.
5. **극적인 목표는 드물고 또렷하게**: 계기 자체가 드물다(사망률이 낮고 중상 중 일부만 반응). 인위적인 상한 대신 진단으로 몰림을 확인한다.

### 1.3 범위

| In | Out |
|---|---|
| 목표 칸·정의 표·생성·다시 계산·교체·단계·결말·알림 지점 | 새 활동 종류를 많이 더하기 |
| 활동 배율, 대상(던전·매물) 지정, 파티 규칙 | 활동 판정 공식 변경 |
| 목표 화제, 검사 창 한 줄, 부탁 칸 연결 | LLM이 줄거리나 결말을 정하는 것 (LLM은 대사만) |
| 1단계: 소문 확인(이관)·장비 마련·원수 갚기·설욕 | 플레이어를 대상으로 한 목표(플레이어에게 복수 등, AMBITION P5) |
| 이후: 몸 추스르기·동료와 원정·복수·라이벌·재기·떠남·빚·네임드 설욕·이주 이관 | 출산·인구 증가(마을 인구는 추상, 경계 문서 §2) |
| | 목표를 통한 전투력 상승 장치 |

## 2. 핵심 개념

### 2.1 세 층

| 층 | 기간 | 어디서 생기나 | 저장 |
|---|---|---|---|
| **야망** (Ambition) | 평생 | 성격에서 계산 | 안 함 |
| **단기 목표** (Objective) | 며칠 | 사건이나 상황 | 지금 목표 1개만 |
| **활동** (Activity) | 몇 시간 | 효용 선택 | 함 |

골드 부족·가방 가득·회복 직후 같은 **필요**는 목표가 아니라 순간 상태라서 지금처럼 둔다.

### 2.2 목표 칸과 우선순위

- NPC 한 명은 목표를 **최대 1개** 가진다.
- 목표는 **분류**와 **우선순위**를 가진다. 분류 순서는 강제 > 극적 > 일상이다. 같은 분류 안에서는 정의 표의 `Priority`를 비교한다.
- 새 목표 후보가 지금 목표보다 높으면 밀어낸다. 낮으면 버린다.
- **같은 종류**의 새 계기가 오면 정의 표의 `SameKindRefresh`를 따른다. Y면 더 나은 대상으로 바꾸고(소문 확인: 가장 좋은 유망한 소문, 장비 마련: 교체 후 전투력이 더 높은 매물), N이면 지금 것을 유지한다.
- 목표가 칸에서 나가는 방식은 둘뿐이다.

| 구분 | 언제 | 결과 |
|---|---|---|
| **끝남** | 이룸, 꺾임 | 결말을 기록한다(극적 목표는 Deed). **다시 생기지 않는다** |
| **빠짐** | 더 높은 목표에 밀림, 대상 던전·매물이 없어짐, 이주 | 지우고 기록하지 않는다. **칸이 빌 때 다시 계산해서 조건이 맞으면 다시 생긴다**(§4.8) |

- 대상이 없어졌거나 이주한 경우는 다시 계산할 때 조건이 맞지 않으니 저절로 돌아오지 않는다. 따로 처리하지 않는다.

### 2.3 흐름

```
계기(사건 또는 상황) ──▶ 후보 판정(조건·대상·성격) ──▶ 목표 칸 비교(분류·우선순위)
                                │ 실패 → 아무 일 없음
                                ▼
                  [준비 단계] ──▶ 실행 단계 ──▶ 칸에서 나감
                  (정의에 있을 때만)              ├ 끝남: 이룸·꺾임 → (극적이면) Deed, 결말 화제
                                                ├ 빠짐: 밀림·대상 없어짐·이주 → 기록 없음
                                                └ 주인 사망 → 그 죽음이 관계자의 계기가 될 수 있음
                                ▲                       │
                                └── 칸이 비면 다시 계산 ◀┘  (최근 14일 기록에서 후보를 다시 모음)
```

### 2.4 1단계 목표 한눈에

| Id | 목표 | 분류 | 계기 | 끝 | 비고 |
|---|---|---|---|---|---|
| 1 | **소문 확인** | 일상 | 유망한 소문 보유 | 그 던전에 다녀옴 | 기존 확인 원정(D76) 이관 |
| 2 | **장비 마련** | 일상 | 상점에서 돈이 모자라 못 산 업그레이드 | 그 장비 칸을 업그레이드함 | 새 목표, 활동 배율 없음 |
| 101 | **원수 갚기** | 극적 | 던전 원정에서 가족·친구·동료가 죽음 | 그 던전이 닫힘 | 기존 "설욕 사망형" |
| 102 | **설욕** | 극적 | 던전 원정에서 중상 | 그 던전 원정에 성공 | 기존 "설욕 중상형" |

우선순위는 원수 갚기 > 설욕 > 소문 확인 > 장비 마련이다.

## 4. 공용 틀

### 4.1 정의 표 (시트 `NpcObjective`)

목표 종류 하나 = 행 하나. 동작은 아래 §4.2의 enum 값으로 고르고, 수치와 문구는 행에 적는다. 대화 콘텐츠 표와 같은 원칙이다(NARRATIVE_CONTENT §1.1 "동작은 enum, 데이터 참조는 int").

- `TimeFrom = Event`면 준비 끝·기한을 **계기 사건 시각**에서 센다. 다시 계산해도 같은 값이 나온다(§4.8). 소문 확인의 72h는 지금 규칙(사건 뒤 72h, D76)과 같다.
- 장비 마련은 지금 상점 상태에서 매번 새로 계산하는 목표라 `Created`(칸에 들어온 시각) 기준이다.
- 설욕 준비 72h: 중상은 치료받으면 24h, 못 받으면 72h 누워 있다(치료율 약 77.5%, NAMED_THREAT §6.4 착수 전 확인). 치료받으면 회복 뒤 48h 준비하고, 못 받으면 누워 있는 동안 준비가 끝나 회복하자마자 실행 단계다.
- 표가 넓다. 열은 1단계에 쓰는 것부터 두고, 필요해질 때 더한다.
- 정의 표는 구글 시트의 새 탭 `NpcObjective`로 둔다(D147). 열이 33개라 새 탭 기본 격자(26열, A~Z)보다 많다. 탭을 만들 때 열을 늘리고 다운로드 범위도 함께 맞춘다(Skill 시트에 열을 더할 때 격자와 다운로드 범위를 둘 다 고쳐야 했던 선례).

### 4.2 동작 종류 (enum)

새 목표는 대부분 행만 더한다. 새로운 계기·대상·완료 조건이 필요할 때만 enum 값과 처리 코드를 하나씩 더한다. 모든 enum은 끝에만 추가한다.

```csharp
// 제안 예시. 아직 구현되지 않았다.
public enum NpcObjectiveCategory { None = 0, Daily = 1, Dramatic = 2, Forced = 3 }   // 값이 클수록 우선
public enum NpcObjectiveTrigger { None = 0, PromisingRumor = 1, UnaffordableUpgrade = 2,
                                  CompanionFellInDungeon = 3, SevereWoundInDungeon = 4 }
public enum NpcObjectiveTargetKind { None = 0, Dungeon = 1, ShopItem = 2 }
public enum NpcObjectiveComplete { None = 0, VisitDungeon = 1, UpgradeSlot = 2,
                                   DungeonClosed = 3, ExpeditionSuccess = 4 }
public enum NpcObjectiveReactProfile { None = 0, Loyal = 1, Proud = 2 }               // 성격 배율 규칙 (§6.2)
public enum NpcObjectiveTimeFrom { Created = 0, Event = 1 }
public enum NpcObjectiveStage { None = 0, Preparing = 1, Attempting = 2 }            // 계산값, 저장하지 않음
```

### 4.3 생성

계기는 두 가지 모양이다.

| 모양 | 언제 판정 | 1단계 예 |
|---|---|---|
| **사건형** | 그 사건이 일어난 순간 1회 + 칸이 빌 때 다시 계산(§4.8) | 원수 갚기(사망), 설욕(중상), 장비 마련(거래 종료) |
| **조건형** | Idle 전환(활동 선택 직전)마다 | 소문 확인(유망한 소문 보유) |

생성 순서:
1. 계기 조건 확인 (정의 행의 `Trigger` 처리).
2. 대상 결정·유효 확인 (던전이 소속 마을 슬롯에 있는가, 매물이 재고에 있는가).
3. 이미 **끝난** 목표인지 확인 (같은 정의·같은 대상의 결말 Deed가 있는가, §4.8).
4. 목표 칸 비교 (§2.2). 지면 여기서 끝. 같은 종류면 `SameKindRefresh`.
5. 생성 확률 = `ReactChance` × 관계 배율(원수 갚기) × 성격 배율(`ReactProfile`, §6.2). 1이면 굴리지 않는다.
6. 칸에 넣는다. 밀린 목표는 **빠짐**으로 지운다.

### 4.4 단계

- `PrepHours`가 0이면 바로 실행 단계다.
- 단계는 저장하지 않고 계산한다: 지금 시각 < 기준 시각 + `PrepHours`면 준비, 아니면 실행. 기준 시각은 `TimeFrom`이 정한다.
- 부상 중인 NPC는 원래 활동을 고르지 않으므로, 회복 중에 준비 시간이 흘러도 문제가 없다.
- 단계마다 정의 행의 배율이 활동 점수에 곱해진다(§7).

### 4.5 칸에서 나갈 때

| 결과 | 조건 | 남는 것 |
|---|---|---|
| **끝남 — 이룸** | `Complete` 조건 충족 | `RecordDeed`면 `ObjectiveFulfilled` Deed. 결말 화제(`FulfilledText`) |
| **끝남 — 꺾임** | 기한 경과, 또는 `MaxAttempts` 소진 | `RecordDeed`면 `ObjectiveAbandoned` Deed. 결말 화제(`AbandonedText`) |
| **빠짐** | 더 높은 목표에 밀림, 대상이 완료 조건 밖의 이유로 없어짐, 주인 이주 | 기록 없음. 걸린 부탁이 있으면 다음 대화에서 알리고 끝. 칸이 빌 때 다시 계산 대상 |
| **주인 사망** | 목표 주인이 죽음 | 목표를 지움. 그 죽음이 다른 NPC의 계기가 될 수 있음(§6.5) |

- 일상 목표는 Deed를 남기지 않는다. 주요 사건 이력을 일상 일로 채우지 않기 위해서다. 일상 목표가 끝났는지는 사실이 바뀐 것으로 안다(소문에 "확인함"이 붙음, 장비를 사서 더 이상 업그레이드가 아님).

### 4.6 알림 지점

목표 판정은 기존 코드의 사건 지점에서 공용 진입점 하나(예: `NpcManager.NotifyObjectiveEvent`)를 부르는 방식으로 연결한다. 게임과 진단이 같은 진입점을 부른다.

| 사건 | 지금 코드 위치 | 목표에 주는 것 |
|---|---|---|
| 던전 원정 귀환(참가자별) | `NpcManager_Delve.ResolveSoloDelve`·`ResolvePartyDelve` | VisitDungeon 완료, ExpeditionSuccess 완료, 시도 +1 |
| 던전 원정 사망 | `System_NpcSim.ResolveDelve`·`ResolvePartyDelve` → `NpcManager.MarkNpcDead` | 사망 Deed에 던전 기록. 사망 정리 **뒤** 같은 마을 생존자의 기억으로 CompanionFellInDungeon 판정 |
| 던전 원정 중상 | `NpcManager_Trade.ApplyExpeditionWound` (Delve, 중상 확정 직후) | 중상 Deed에 던전 기록, SevereWoundInDungeon 판정 |
| 거래 종료 | `NpcManager_Trade.TradeAtShop` | UpgradeSlot 완료, UnaffordableUpgrade 계기·같은 종류 갱신, 매물 유효 확인 |
| NPC 던전 완료 | `NpcManager_Rumor.OnNpcDungeonCompleted` | DungeonClosed 완료(본인·남) |
| 플레이어 던전 완료 | `NpcManager_Narrative.StageDungeonCompletion` | DungeonClosed 완료(플레이어·동행) |
| NPC 사망(모든 경로) | `NpcManager.MarkNpcDead` | 주인 사망 정리 |
| 이주 시작 | `NpcManager_Relocation` | 빠짐 |

### 4.7 평가 시점

- **사건 시점**: 사건형 계기 판정, 완료·시도 집계, 주인 사망.
- **Idle 전환 때**: 조건형 계기, 기한 확인, 대상 유효 확인, 같은 종류 갱신(§5.1).
- **칸이 빈 직후의 Idle 전환 1회**: 다시 계산(§4.8). 칸이 빈 채로 있어도 매번 다시 계산하지 않는다. 그 뒤로는 새 사건과 조건형 계기만 기다린다.
- 매 틱 검사하지 않는다. 화면 안과 밖이 같은 규칙이다.

### 4.8 다시 계산 — 빠진 목표가 돌아오는 방법

빠진 목표는 따로 보관하지 않는다. 그 목표를 만든 **사건 기록은 NPC에게 원래 남아 있으므로**, 칸이 빌 때 그 기록에서 후보를 다시 모은다. AMBITION D70(계산할 수 있는 값은 저장하지 않는다)과 같은 원칙이다.

**언제**: 지금 목표가 끝나거나 빠져서 칸이 빈 뒤 첫 Idle 전환 때 1회.

**무엇을 보나** — 최근 14일(극적 목표 기한) 안의 기록만 본다. 기록은 최근 것부터 거꾸로 훑다가 14일보다 오래된 것이 나오면 멈춘다. 그보다 오래된 기록은 계산하지 않는다.

| 목표 | 다시 만드는 근거 | 이미 끝났는지 판별 |
|---|---|---|
| 소문 확인 | 소문 목록 (조건형이라 원래 매번 봄) | 다녀오면 소문에 "확인함"이 붙어 후보가 아님 |
| 장비 마련 | 소속 마을 상점 재고 + 지금 골드 | 사면 더 이상 업그레이드가 아님 |
| 설욕 | 본인의 중상 Deed(던전·시각) | 같은 던전의 설욕 결말 Deed가 있으면 제외 |
| 원수 갚기 | 본인의 사망 관계 기억·공동 활동 기억 → 죽은 NPC의 사망 Deed(던전·시각, 사망자 최소 기록에 남음) | 던전이 닫혔으면 제외, 같은 사망자의 꺾임 Deed가 있으면 제외 |

- 후보를 모두 모은 뒤 §4.3의 순서대로 판정하고, 통과한 후보 중 가장 높은 것 하나를 세운다.
- **성격 판정은 결정론이라 다시 굴려도 같다.** 같은 NPC·같은 사건 시각이면 salt 200의 결과가 같다. 한 번 묻어 두기로 한 NPC가 다시 계산할 때마다 운 좋게 통과하는 일은 없다.
- **단계와 기한은 사건 시각에서 계산하므로 그대로 이어진다.** 준비 기간이 이미 지났으면 바로 실행 단계다.
- **시도 횟수만 처음부터다.** 실제 원정 기록이 없어 계산할 수 없다. 기한이 사건 기준으로 고정이라 무한히 이어지지는 않는다.
- **밀려 있는 동안 기한이 끝난 목표는 돌아오지 않는다.** "원수 갚기에 매달리느라 설욕은 놓쳤다"로 본다. 이 경우만 조용히 끝나며, 플레이해 보고 어색하면 결말 화제에 한 줄 덧붙인다(§14 Q11).

**예시 (영희)**

| 때 | 일 | 목표 칸 | NPC 기록에 남은 것 |
|---|---|---|---|
| 1일 | 서쪽 던전에서 중상 | 서쪽 설욕 | 중상 Deed(서쪽 던전, 1일) |
| 3일 | 동생 철수가 동쪽 던전에서 죽음 | 원수 갚기 (설욕은 빠짐) | 위 + 사별 기억(철수). 철수의 사망 Deed(동쪽 던전, 3일) |
| 9일 | 동쪽 던전이 닫혀 원수 갚기 이룸 | 비어 있음 → 다음 Idle 전환 때 다시 계산 | 위 + 원수 갚기 이룸 Deed |
| 9일 | 다시 계산: 철수 건은 던전이 닫혀 제외, 서쪽 중상은 8일 전이라 기한 안 | **서쪽 설욕이 다시 섬** (기한 15일까지, 준비는 이미 지나 실행 단계, 시도 0회부터) | |

## 5. 일상 목표

### 5.1 소문 확인 (1) — 기존 확인 원정 이관

**지금** (D76): 활동을 고를 때마다 유망한 소문(들은 원정 성공, 가치 ≥ 20, 사건 뒤 72h 이내, 미확인, 유효)이 있는지 본다(`TryGetPromisingRumor`). 있으면 던전 원정 ×1.5. 원정을 떠날 때 리더의 유망한 소문 중 가치가 가장 높은 소문의 슬롯으로 간다(`PickConfirmationDelveSlot`). 돌아온 참가자의 그 슬롯 소문에 `Checked`가 붙는다. [src: Assets/Scripts/Manager/NpcManager_Rumor.cs, Assets/Scripts/Manager/NpcManager_Delve.cs `TryPrepareDelveTarget`]

**바뀐 뒤**:
- Idle 전환 때 유망한 소문이 있고 목표 칸이 비었거나 더 낮은 목표(장비 마련)면 **소문 확인 목표**를 만든다. 대상은 지금과 같은 규칙으로 고른 소문의 던전이고, 기한은 그 소문 사건 시각 + 72h다.
- 목표가 이미 있으면 Idle 전환 때마다 대상을 지금 규칙의 "가장 좋은 유망한 소문"으로 다시 맞춘다(`SameKindRefresh`). 유망한 소문이 없어지면(무효·만료·확인됨) 목표는 빠진다.
- 활동 배율은 정의 행의 실행 단계 던전 원정 ×1.5다. 지금 `HasPromisingRumor` 필요 배율을 대신한다.
- 원정 대상은 리더의 목표 던전이 먼저다(`PickConfirmationDelveSlot` 호출을 대신). 확인 원정 집계·소문 노출 기록은 그대로 남긴다.
- 원정에서 돌아오면 그 던전을 목표로 가진 참가자의 목표가 이룸으로 끝난다. 소문의 `Checked` 표시는 소문 데이터라 그대로 둔다.
- 진행 중 화제는 없다(`StatusText` 빈칸). 기존 소문 화제가 이미 같은 이야기를 한다. 검사 창에는 "목표: 동쪽 던전 소문 확인"이 보인다.

**같게 지킬 것**: 던전 원정 선택 비중(4~6%), 확인 원정 비율(던전 원정의 약 28%, AMBITION §7.4 관측값), 소문 지표. 1단계 본체 진단에서 이관 전후를 비교한다.

**달라지는 점**: 극적 목표를 가진 NPC는 소문 확인 목표를 받지 않는다. 극적 목표가 끝난 뒤 그 소문이 아직 유망하면 다음 Idle 전환 때 돌아온다. 극적 목표는 드물어서 세계 지표에는 영향이 거의 없을 것이다. [추론]

### 5.2 장비 마련 (2) — 새 목표

**지금**: 거래 때 예산(Gold − 치료비 예비금) 안의 업그레이드 매물 중 가장 좋은 1개만 산다. 예산을 넘는 매물은 업그레이드인지 따져 보지도 않고 건너뛴다. 업그레이드 문턱은 전체 전투력 +15%이고, 상한의 80%를 넘었으면 +30%다(D45). [src: Assets/Scripts/Manager/NpcManager_Trade.cs `FindBestShopUpgrade`]

**바뀐 뒤**:
- **계기**: 거래가 끝날 때, 예산만 넘어서 못 산 업그레이드 매물(재고 조건·D45 문턱·개인 상한 통과)이 있으면 그중 교체 후 전투력이 가장 높은 1개를 목표로 세운다. 칸이 빌 때 다시 계산하면 같은 방법으로 지금 재고를 다시 본다.
- **같은 종류 갱신**: 장비 마련 중에 거래에서 더 좋은 매물을 보면 대상만 바꾼다(`SameKindRefresh`).
- **대상**: 그 매물(기본 아이템 행, 표시 이름, 가격, 장비 칸).
- **완료**: 거래에서 그 장비 칸을 업그레이드하면 이룸이다. 같은 물건이 아니어도 된다. 다른 물건을 샀으면 결말 화제에 실제로 산 물건 이름이 들어간다.
- **빠짐**: 매물이 재고에서 없어짐(재고 회차가 바뀜), 더 이상 업그레이드가 아님(개인 상한 도달 등).
- **꺾임**: 7게임일 기한. 일상 목표라 Deed는 없다.
- **진행 표시**: 지금 Gold / (가격 + 치료비 예비금). 진행 값은 저장하지 않는다. 그래서 빠졌다가 다시 생겨도 잃는 것이 없다.
- **활동 배율 없음**(모두 1.0). 닫힌 경제의 골드 흐름 기준(GOLD_BALANCE §11.2)을 흔들지 않기 위해서다. 플레이해 보고 필요하면 사냥·거래 배율을 작게 더한다(§14 Q6).

**지금 → 바뀐 뒤 → 예시**: 민수는 지금도 골드가 모이면 언젠가 철 도끼를 사지만, 그 일은 대화에 드러나지 않는다. 바뀐 뒤에는 거래가 끝날 때 "장비 마련: 철 도끼" 목표가 생기고, 검사 창에 "목표: 철 도끼 사기 (42/80골드)"가 보인다. 말을 걸면 "철 도끼 살 돈을 모으는 중이오. 아직 38골드가 모자라오."라고 한다. 나중에 사면 사흘 동안 "드디어 철 도끼를 샀소!"라고 말한다.

**빈도 주의**: NPC 구매는 원래 드물다(30일 실행 구매 226건, GOLD_BALANCE §11.2). D45 문턱 때문에 업그레이드 자체가 드물어서, 장비 마련 목표도 자주 생기지 않을 수 있다. 1단계 본체 진단에서 빈도를 센다. 많은 NPC가 목표를 갖는 효과는 1단계에서는 주로 소문 확인(유망한 소문 보유율 약 19%, AMBITION §7.4)에서 나온다. 2단계 일상 목표(§11)로 넓힌다.

**겹침 정리**: 업그레이드를 사면 기존 자랑 화제(주요 아이템 Deed)도 나올 수 있다. 같은 구매를 두 번 말하지 않게 구현 때 정리한다. 개인 사연 자리 경쟁 때문에 자랑 화제가 거의 안 나오는 문제(D109 ①)를 결말 화제가 일부 대신할 수도 있다. [추론]

## 6. 극적 목표: 원수 갚기 (101) · 설욕 (102)

### 6.1 계기

| 목표 | 계기 | 판정하는 NPC | 대상 던전 |
|---|---|---|---|
| **원수 갚기** | 솔로·파티 던전 원정에서 NPC가 죽음 | 죽은 NPC와 **같은 마을**에 사는 생존자 중 사망 관계 기억(가족·친구·사제)이나 공동 활동 기억(함께 원정한 동료)이 있는 NPC **전원이 각자** | 죽은 NPC의 사망 Deed에 남긴 던전 |
| **설욕** | 던전 원정에서 중상 | 본인 | 중상 Deed에 남긴 던전 |

- **같은 마을만**: NPC 던전 원정은 소속 마을 슬롯만 간다(D68·D75). 다른 마을에 사는 형제는 그 던전에 갈 수 없으므로 판정하지 않는다.
- **각자 판정**: 관계자마다 자기 기억과 자기 성격으로 따로 판정한다. 같은 죽음을 여러 명이 쫓을 수 있다. 배우자와 형제가 함께 원수를 갚으러 가는 쪽이 이야기로도 낫고, 다시 계산이 남의 상태를 보지 않아도 되어 단순하다.
- **판정 시점**: 사망 정리(`MarkNpcDead`)가 생존자에게 사망 관계 기억과 공동 활동 기억을 남긴 **뒤** 판정한다. 그래서 사건 시점 판정과 다시 계산이 같은 기록을 같은 방식으로 읽는다. 설욕은 `ApplyExpeditionWound`가 중상을 확정한 직후다. [src: Assets/Scripts/Manager/NpcManager.cs `MarkNpcDead`·`RecordDeceasedRelationMemories`, Assets/Scripts/Manager/NpcManager_SharedActivities.cs]
- **던전 기록**: 던전은 생존자 기억마다 넣지 않고 **죽은 NPC 자신의 사망 Deed에 한 번** 남긴다. 죽은 NPC의 기록은 사망자 최소 기록으로 줄어들지만 사망 Deed(시각·던전)는 남으므로([NPC_SIMULATION §5.2](NPC_SIMULATION_DESIGN.md)) 모든 생존자가 거기서 읽는다. 공동 활동 기억에는 사망 시각·던전이 없어서 이 방식이 필요하다.

### 6.2 반응 판정과 빈도

```
생성 확률 = ReactChance × 관계 배율 × (1 + clamp(성격 항, ±0.5))       (각 성격 수치 50을 0으로 둔 ±값)
  관계 배율 (원수 갚기만, 여러 개면 가장 높은 것)
    가족 — 배우자·형제·부모·자식(Spouse·Sibling·ParentOf 양방향)  ×1.0
    친구·사제 (Friend·MentorOf)                                    ×0.7
    함께 원정한 동료 — 공동 활동 기억, 사망 때 호감(LastAffinity) 50 이상  ×0.5
    라이벌·원한 관계(Rival·GrudgeAgainst)만 있으면                   제외
  Loyal (원수 갚기, 0.60) — 충성 +0.25, 자존심 +0.15, 용기 +0.10, 인내 −0.20
  Proud (설욕, 0.25)     — 자존심 +0.25, 용기 +0.20, 안전 야망 주 −0.30 / 보조 −0.15
```

- 결정론 RNG(소유자 = 판정하는 NPC의 EntityId, 시각 = 사건 시각, salt 200). 다시 계산해도 결과가 같다(§4.8).
- 같은 사건이라도 인내가 높은 NPC는 묻어 두고, 충성·자존심이 높은 NPC는 목표를 세운다.
- 반응하지 않으면 지금처럼 사별 화제·부상 화제만 남는다.

**빈도 추정**: 원정 부상은 30일에 약 25,900건이고 그중 약 10%가 중상이다(D92). 사망은 30일 실행에서 0.42~0.71%(약 2,400명 기준 10~17명)다(GOLD_BALANCE §11.2). 던전 원정의 몫은 아직 따로 집계하지 않았다. [추론] 던전 원정이 중상의 15%라면 30일에 약 390건, 반응 25%면 약 100건이다. 300개 마을로 나누면 마을당 0.3개 정도다. 던전에서 죽는 NPC는 세계 전체에서 한 달에 몇 명 수준일 것이라 **원수 갚기는 드물게 마주치는 큰 사건**이고, 플레이어가 자주 보는 극적 목표는 설욕이다. 1단계 본체 진단에서 함께 센다(§12).

### 6.3 단계

| 단계 | 기간 (사건 시각 기준) | 효과 (정의 행) |
|---|---|---|
| **준비** | 원수 갚기: 사망 뒤 48h / 설욕: 중상 뒤 72h | 사냥 ×1.25, 거래 ×1.5(할 일이 있을 때만), 휴식 ×0.8, 던전 원정 ×0.5 |
| **실행** | 준비 끝 ~ 결말 | 던전 원정 ×4(대상 = 목표 던전), 휴식 ×0.8, 모집 시도 항상, 다른 리더의 모집 후보에서 빠짐(같은 대상 리더는 예외) |

- 준비 단계의 거래 배율은 구매 기회를 늘리지만, 구매 쿨다운 48h(§7.2)와 개인 상한이 있어 전투력은 크게 오르지 않는다. 진단의 "전투력 +10% 이내" 기준으로 확인한다.
- 실행 단계 던전 원정 비중 추정: 기본 점수 합 약 2.35에 던전 원정 0.10 × 4를 넣으면 한 번 고를 때 약 15%다(거래할 일이 없으면 약 20%). 활동 평균 길이를 6시간으로 보면 1~2게임일 안에 첫 시도가 나온다. [추론]

### 6.4 결말

| 결말 | 조건 | 남는 것 |
|---|---|---|
| **이룸 — 극복** (설욕) | 실행 단계의 목표 원정 결과가 성공 | `ObjectiveFulfilled` Deed. "다시 가서 이겨 냈소." |
| **이룸 — 직접** (원수 갚기) | 목표 주인(또는 그 파티)이 대상 던전을 완료 | `ObjectiveFulfilled` Deed. NPC 완료는 성공 시 3~8%라 드물다(D55) |
| **이룸 — 함께** (원수 갚기) | 목표 주인을 동행으로 데려간 플레이어 측이 대상 던전 보스를 처치 | `ObjectiveFulfilled` Deed. 행적 반응은 부탁한 NPC(×3) 기준 |
| **이룸 — 대신** (원수 갚기) | 플레이어 측이 동행 없이 대상 던전 보스를 처치 | `ObjectiveFulfilled` Deed. 부탁했으면 보고·보답(§8.3), 안 했으면 "소문 전 해결"처럼 직접 말하기 대화(보답 없음) |
| **이룸 — 남이** (원수 갚기) | 다른 NPC 파티가 대상 던전을 완료 | `ObjectiveFulfilled` Deed. `FulfilledByOtherText`(성격에 따라 안도·허탈은 LLM 표현) |
| **꺾임** | 사건 뒤 14게임일, 또는 시도 3회가 모두 실패·부상 | `ObjectiveAbandoned` Deed. 체념 화제 |

- 시도는 목표 던전으로 간 원정 1회마다 센다. 원수 갚기에서 원정이 성공해도 던전이 닫히지 않으면 이룸이 아니고 시도만 쌓인다.
- 같은 죽음을 쫓는 주인이 여럿이면 던전이 닫히는 순간 모두 이룸이다. 같은 파티로 닫았으면 모두 "직접", 다른 사람이 닫았으면 모두 "남이"다.
- 원수 갚기는 NPC 혼자서는 이루기 어렵다. 플레이어가 끼어들 자리가 여기서 생긴다. 꺾임이 너무 많으면 "목표 원정 성공 2회 = 이룸"을 더하는 안을 검토한다(§14 Q3).
- 던전이 닫혔는지는 저장한 `DungeonId`가 소속 마을 현재 슬롯에 있는지로 판정한다(D68과 같은 방식). 누가 닫았는지는 §4.6의 두 완료 알림이 알려 준다.

### 6.5 연쇄

- 목표 주인이 **목표 던전 원정에서** 죽으면, 그 죽음은 일반 규칙(§6.1)대로 관계자의 원수 갚기 계기가 된다.
- **상한을 두지 않는다**(D148). 연쇄는 저절로 멈춘다. [추론, 진단 수치로 거칠게 계산]
  - 30일 동안 세계 원정(사냥 + 던전)은 약 10만 번, 사망은 10~17명이라 원정 1회 사망 확률은 0.01~0.02%다. 던전 원정이 몇 배 위험하다고 쳐도 1회 0.1%를 넘기 어렵다.
  - 목표 주인은 시도가 최대 3회라 목표 원정 중 죽을 확률은 0.3% 이하다. 거기에 같은 마을 관계자·성격 판정·던전이 아직 열려 있음이 겹친다.
  - 그래서 죽음 하나가 다음 죽음을 낳을 기대값은 0.01도 안 된다. 사망률을 일부러 아주 낮게 잡은 설계(D48) 덕분이다.
- 연쇄 깊이는 저장하지 않는다. 진단에서 연쇄 건수만 본다.
- 1단계에서는 이룸·꺾임이 다른 NPC의 계기가 되지 않는다. 이후 꺾임 → 재기·떠남을 붙인다(§11).

## 7. 활동 선택과의 연결

### 7.1 배율

- `NpcActivityChoiceContext`에 목표가 주는 활동별 배율 네 개를 더하고, `GetActivityScore`가 곱한다. 지금의 `HasPromisingRumor` 필드는 소문 확인 목표가 대신한다.
- 성향 ±20% 클램프 밖에서 곱한다(D40의 "필요는 성향과 별개" 규칙과 같다).
- 목표는 **확률을 기울이기만** 한다(D146). 목표가 있어도 그 활동만 하지 않고, 휴식·사냥·거래가 섞인다.
- 배율 계산은 정적 순수 규칙(예: `NpcObjectiveRules`)에 두고 게임과 진단이 같은 메서드를 부른다.

**보통 성격 NPC의 선택 확률** (%, "거래할 일 있음 / 없음")

| 상태 | 휴식 | 사냥 | 거래 | 원정 |
|---|---|---|---|---|
| 목표 없음 | 38 / 49 | 36 / 46 | 21 / — | 4 / 5 |
| 소문 확인 | 38 / 47 | 35 / 45 | 21 / — | 6 / 8 |
| 장비 마련 | 38 / 49 | 36 / 46 | 21 / — | 4 / 5 |
| 원수 갚기·설욕 준비 | 28 / 39 | 41 / 58 | 29 / — | 2 / 3 |
| 원수 갚기·설욕 실행 | 29 / 37 | 34 / 43 | 20 / — | 16 / 20 |

### 7.2 대상과 파티

- **던전 대상**: `TryPrepareDelveTarget`의 순서를 "목표 던전(리더의 목표) → 균등 선택"으로 바꾼다. 지금의 "유망한 소문" 단계는 소문 확인 목표가 대신한다. [src: Assets/Scripts/Manager/NpcManager_Delve.cs `TryPrepareDelveTarget`]
- **모집 시도**: `AlwaysRecruit`가 Y인 목표의 주인이 목표 원정을 고르면 모집 시도 확률(D86)을 건너뛰고 항상 모집한다.
- **수락 보너스**: 원수 갚기 원정이면 죽은 NPC의 사망 관계 기억이나 공동 활동 기억이 있는 후보의 수락 확률에 +0.20(상한 0.90 유지).
- **다른 파티**: `SkipOtherParties`가 Y인 목표의 주인은 실행 단계에서 다른 리더의 모집 후보에서 빠진다. 단 **같은 대상을 노리는 리더**의 모집에는 후보로 남는다. 같은 죽음을 쫓는 두 사람이 따로 솔로로 가지 않게 하기 위해서다.

### 7.3 세계 지표 영향

일상 목표는 기존 동작을 옮긴 것(소문 확인)이거나 배율이 없다(장비 마련). 극적 목표는 계기 자체가 드물다(§6.2). 그래서 세계 활동 비중 변화는 작을 것이다. [추론] 구현 뒤 진단으로 기존 기준을 다시 확인한다 — 던전 원정 비중 4~6%, 사냥 38±5%(D56 개정), 30일 사망 0.5~1%, 전투력 +10% 이내, 개인 상한 초과 0, 닫힌 경제 검산 0, 구매 수.

## 8. 플레이어가 만나는 길

### 8.1 검사 창

성향 탭의 "야망" 줄 아래에 목표 한 줄을 더한다(`InspectText`). 예: "목표: 철 도끼 사기 (42/80골드)", "목표: 철수의 원수를 갚는다 — 준비 중". 목표가 없으면 줄을 보이지 않는다. [src: Assets/Scripts/UI/UINpcInspect.cs 야망 표시]

### 8.2 대화

- **진행 중 화제**(`StatusText`): 극적 목표는 **고정(Pinned)** 화제다. 지금 부탁·소망 화제처럼 레퍼토리에 반드시 들되 다른 화제와 번갈아 나온다. 개인 사연 2자리 경쟁(D109 ①)에 끼지 않게 하기 위해서다. 일상 목표는 고정하지 않는 일반 화제다. [src: Assets/Scripts/Manager/NpcManager_NarrativeDialogue.cs, Assets/Scripts/Manager/NpcManager_NarrativeWish.cs]
- **결말 화제**: `OutcomeTopicHours` 동안 나오는 일반 화제다.
- 시스템이 사실(대상·계기 인물·단계·결말·진행 값)을 정하고 LLM은 말투만 입힌다. LLM이 없으면 표의 문구 그대로 나온다.

### 8.3 부탁 — 지금 구조를 그대로 쓴다

- 조건: `RequestAffinity`가 0보다 큰 목표(1단계는 원수 갚기만), 실행 단계, 플레이어 호감이 그 문턱 이상, 부탁 칸이 빔.
- 부탁 대사가 실제로 표시된 뒤 narrative 원장에 목표 부탁 인스턴스를 만들고 부탁 칸(`NpcNarrativeRequest`)에 넣는다. 소망처럼 미리 만들지 않는다.
- 해결 = 플레이어 측(동행 포함)이 목표 던전 보스를 처치. 보고·반응·의뢰 보답·`PlayerDeed` 소문 전파는 NARRATIVE_CONTENT §4.1·§4.5와 같다.
- **같은 던전을 여러 NPC가 부탁해도 된다**(D151). 부탁마다 인스턴스가 따로라서 각자 반응하고 각자 의뢰 보답(10~20골드, 시스템 생성)을 준다. 보스 한 번에 늘어나는 골드는 작다. 이웃은 같은 보스 처치를 두 건의 행적 소문으로 들을 수 있지만, 한 대화에서 행적을 묶어 반응하는 기존 규칙(최대 3개)으로 대부분 한 번에 합쳐진다. 소문 부탁과 목표 부탁이 같은 던전에 걸려도 같다.
- 목표가 꺾이거나 빠지면 부탁도 끝난다. 다음 대화에서 알리고 보답·전파는 없다(소문 부탁이 미해결로 끝날 때와 같음). 나중에 다시 계산으로 목표가 돌아오면 부탁은 새로 할 수 있다.

### 8.4 동행

목표 주인에게 동행을 요청하면 지금 동행 규칙(던전 전용, D97)대로 함께 간다. 그 던전에서 보스를 처치하면 "이룸 — 함께"다. 동행 수락 조건은 지금 항상 수락이며, 목표와 묶어 바꿀지는 §14 Q2와 함께 정한다. [src: Assets/Scripts/Manager/NpcManager_Companion.cs `RequestCompanion`]

- `NpcSaveData.Objective`와 `NpcSaveData.LastObjectiveOutcome`은 없으면 `null`이고 저장하지 않는다. 목표가 없는 NPC의 저장 크기는 늘지 않는다.
- **단계·기한은 저장하지 않는다.** 정의 행과 `EventGameTime`·`CreatedGameTime`에서 계산한다(D70 원칙). 빠진 목표도 저장하지 않는다(§4.8).
- 저장 그룹은 새 비트(`NpcSaveGroup.Objective`)를 추천한다. 목표 변화가 Deeds·Stories 저장을 같이 끌고 가지 않게 하기 위해서다.
- **Deed 필드 추가** (모두 기본값이면 저장 생략, 기존 Deed 크기는 그대로):
  - `DungeonId` — 던전 원정 사망(`Fell`)과 중상(`SevereWound`) Deed가 그 던전을 남긴다. 사망 정리·중상 기록 호출부가 원정 결과의 던전을 넘긴다. 사냥에서 생긴 사망·중상은 비운다. 사망 Deed는 사망자 최소 기록에 남는 항목이다([NPC_SIMULATION §5.2](NPC_SIMULATION_DESIGN.md)).
  - `ObjectiveDefinitionId` — 결말 Deed가 어떤 목표였는지 담는다. 결말 Deed는 `DungeonId`도 함께 남겨 "이미 끝난 목표" 판별(§4.8)에 쓴다.
- 결말 Deed: `NpcDeedKind`의 예약 번호 `ObjectiveFulfilled = 16`, `ObjectiveAbandoned = 17`을 쓴다(18은 네임드 위협이 이미 씀). 원수 갚기는 참가자에 죽은 NPC를 넣는다.
- 로드 보정: 정의 표에 없는 `DefinitionId`, 범위를 벗어난 시도 횟수는 지우거나 자른다. 대상이 없어졌으면 다음 Idle 전환 때 판정이 처리한다.
- 기존 세이브는 목표 없이 시작한다. 기존 사망·중상 Deed에는 던전이 없어서 그 기록으로는 원수 갚기·설욕이 생기지 않는다. 소문 확인은 다음 Idle 전환 때 조건형으로 다시 생기므로 이관 전 동작이 이어진다.
- 세이브 버전은 올리지 않는다. 새 필드는 기본값 생략, 새 enum 값은 끝에 추가한다(AMBITION §12 저장 규칙).

## 10. 결정론 · LOD · 코드 배치

- **RNG salt**: 200 = 극적 목표 생성 판정(소유자 = 판정하는 NPC, 시각 = 계기 사건 시각 — 사건 시점 판정과 다시 계산이 같은 결과를 낸다). 201~209 = 단기 목표 예비. 일상 목표는 1단계에서 RNG를 쓰지 않는다. 구현 때 NPC_SIMULATION §11.1 salt 정본의 예약 줄을 실제 사용으로 바꾼다. (210~239는 네임드 위협이 쓴다.)
- **코드 배치**: 새 System을 만들지 않는다.
  - 상태: `NpcSaveData.Objective`·`LastObjectiveOutcome`.
  - 도메인 처리: `NpcManager_Objective.cs`(partial) — 후보 판정·다시 계산·교체·평가·알림 진입점.
  - 순수 규칙: `NpcObjectiveRules`(static) — 우선순위 비교, 생성 확률, 관계 배율, 단계 계산, 활동 배율.
  - 정의 표: 다른 테이블처럼 `DataManager`가 읽는다.
  - 사건 시점 판정과 다시 계산은 **같은 후보 판정 메서드**를 쓴다. 게임(`System_NpcSim`)과 진단도 같은 공용 메서드를 부른다(진단 복제 함정, AMBITION P4 기록).
- **계산 비용**: 다시 계산은 칸이 빈 직후 1회만 한다. 최근 14일 기록만 거꾸로 훑고, 원수 갚기는 본인의 기억 몇 건과 죽은 NPC의 사망 Deed만 본다. 장비 마련은 거래 기회 판정(`HasTradeOpportunity`)이 이미 하는 재고 순회와 같은 수준이다.
- **던전 안**: 던전 안에서는 월드 시뮬이 멈추므로 목표 시계도 멈춘다. 기한은 게임 시각 기준이라 따로 보정할 필요가 없다.

관찰:
- 장비 마련은 대부분 **빠짐 → 다시 계산**으로 돈다(상점 재고 회차가 바뀌면 대상이 사라짐, §5.2 규칙대로). 검사 창의 대상이 하루 단위로 바뀔 수 있다. 실제 구매로 이루는 경우는 60일 15건이다.
- 원수 갚기는 60일에 10건 생겨 모두 꺾였다 — §13의 "거의 다 꺾임" 위험 그대로다. 플레이어 부탁이 주 해결 경로다(Q3 검토 대상).
- 극적 목표 주인의 Delve 비중(12~18%)은 §6.3 추정(실행 단계 15~20%)보다 조금 낮다 — 준비 단계 시간이 섞여서다.

## 13. 위험과 대응

| 위험 | 대응 |
|---|---|
| 소문 확인 이관이 기존 지표를 바꿈 | 대상 갱신 규칙을 지금과 같게 두고(§5.1), 이관 전후를 진단으로 비교 |
| 극적 목표 원정이 늘어 사망률이 목표를 넘음 | 시도 3회·기한 14일. 넘으면 실행 배율을 낮춘다 |
| 한 마을에 극적 목표가 몰림 | 상한 없이 시작한다(D148). 진단의 마을당 동시 최대값을 보고, 몰리는 목표 종류에만 상한을 둔다 |
| 원수 갚기가 거의 다 꺾임으로 끝나 우울함 | 플레이어 부탁이 주 해결 경로다. 꺾임 비율을 보고 Q3 안을 검토한다 |
| 장비 마련이 거의 안 생김 | 본체 진단에서 빈도를 센다. 넓은 일상 목표는 2단계(몸 추스르기·동료와 원정)로 보완 |
| 소문 확인 ↔ 장비 마련 교체가 잦아 검사 창이 자주 바뀜 | 일상 목표는 진행 값을 저장하지 않아 잃는 것이 없다. 표시가 거슬리면 교체 뒤 짧은 재생성 대기를 둔다 |
| 대화가 목표 이야기로만 채워짐 | 고정 화제는 극적 목표만, 다른 화제와 번갈아 나오는 기존 순환을 따른다 |
| 다시 계산이 이미 끝난 목표를 되살림 | 결말 Deed(정의·던전·사망자)로 끝난 목표를 거르고, 일상 목표는 바뀐 사실로 거른다(§4.8). 진단에서 확인 |
| 다시 계산 비용 | 칸이 빈 직후 1회, 최근 14일 기록만(§10) |
