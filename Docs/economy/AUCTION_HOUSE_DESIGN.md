# 경매장 (온라인 물물교환 시장) 설계
_디자인 확정: 2026-07-23_

> 한 줄: 마을 건물로 접근하지만 **월드 단위 단일 인스턴스**를 공유하는, **시뮬레이션 기반**
> **직접 물물교환** 시장. 아이템의 진짜 가치는 내부적으로 계산되지만 플레이어에게는
> 불확실하게만 보여서, 잘못 거래하면 **사기당할 수 있다**.

---

## 디자인 (durable — 구현 후에도 유효)

### 0. 기존 상인(시장)과의 경계 — 왜 별개 시스템인가

| 축 | 기존 상인(MerchantStall / `ProvidedService.Shop`) | 경매장 (본 문서) |
|---|---|---|
| 상태 범위 | **마을별** (`VillageData.MerchantStock`) | **월드 단위 공유 1개** |
| 통화 | 골드 (`PlayerData.Gold`) | **물물교환** (가치 기반, 골드 미개입 기본) |
| 대상 | 일반 아이템 | **특별한(고티어) 아이템** |
| 가격/재고 | 결정론적 재고 롤 + 골드가 | 결정론적 매물 롤 + **직접 제안/수락** |
| 성사 | 즉시 구매/판매 | 판매자·구매자가 **제안을 수락/거절** |

두 시스템은 데이터 계약·통화·상태 범위가 전부 다르므로 상인 코드를 확장하지 않고 별도
서브시스템으로 짓는다. 가치 산정만 공용 로직으로 뽑아 양쪽이 쓸 수 있게 한다(§3).

### 1. 결정 사항

- **[결정] 매물 공급 = 시뮬레이션 글로벌 시장(싱글플레이어).**
  - 이유: 현재 프로젝트는 로컬 저장(`WorldData.json`) 싱글플레이어. 실제 서버 없이 NPC/AI가
    생성한 가상 매물로 "온라인처럼 보이는" 시장을 만든다.
  - 기각한 대안: 실제 온라인 멀티플레이어 — 백엔드/네트워크/인증 인프라가 전무해 범위 밖.
    (미래에 진짜 온라인으로 승격할 여지는 §구조 의도에서 경계를 열어 둠.)

- **[결정] 상태는 월드 단위 단일 인스턴스.** 어느 마을의 경매장 건물에서 열든 **같은 매물
  풀**을 본다.
  - 이유: 사용자 요구("여러 마을에서 접근해도 하나의 인스턴스로 동기화"). 마을별 소유가
    아니라 월드 소유이므로 `VillageData`가 아니라 `WorldData`에 산다(§구조 의도).

- **[결정] 교환 방식 = 직접 물물교환 제안(수락/거절).** 가치 크레딧(내부 화폐)·자동 매칭은
  기각.
  - 이유: 사용자 선택. "비슷한 가치의 물건과 바꾼다"는 감각을 크레딧 통화로 추상화하지 않고
    실제 아이템 대 아이템 제안으로 유지.
  - 기각한 대안: **가치 크레딧** — 구현·동기화는 가장 단순하나 물물교환 감각과 사기 여지가
    옅어짐. **자동 매칭** — "원하는 것" 지정 UX와 매칭 룰이 무거움. 둘 다 사기 메커니즘(§3)과
    궁합이 나쁨.

- **[결정] 아이템 가치 = `ItemTable.BasePrice`에서 파생한 계산값(True Value), 옵션(모드)에
  따라 달라짐, 그리고 플레이어에겐 불확실하게만 노출.** → **사기(손해 거래)가 가능한 시스템.**
  - 이유: 사용자 요구. 같은 베이스라도 붙은 모드/티어/품질에 따라 실가치가 크게 다르고,
    플레이어가 진짜 가치를 모르면 나쁜 거래를 받아들일 수 있어야 함(게임성의 핵심).
  - 함의: **진짜 가치(True Value)와 표시 가치(감정가, Estimated Value)를 분리**한다(§3).
  - 골드 개입: 교환은 **순수 물물교환**(가치 허용 오차로 성사), 골드 미개입으로 확정.

- **[결정] 감정가는 항상 오차 밴드로만 노출. 감정(Appraisal) 완화 기능은 도입 안 함(미래 유보).**
  - 이유: 사용자 결정. 사기·득템을 눈썰미·경험 기반 도박으로 유지하고 시스템을 단순하게
    출발. 필요해지면 나중에 밴드를 좁히는 감정 기능을 얹을 수 있음(구조는 열어 둠).
  - 함의: 정확 실가치는 절대 노출 안 함(항상 밴드). 골드는 교환에도 감정에도 쓰이지 않음 —
    유일한 골드 싱크 후보는 등록비/성사 수수료(열린 질문).

- **[결정] 거래 대상 자격 = 아이템 티어 기준.** `ItemTable.Tier >= AuctionMinTier`인 아이템만
  경매장에서 거래 가능.
  - 이유: 사용자 선택. 일반 소모품·재료는 기존 상인, 특별한 고티어 아이템은 경매장으로
    자연 분리. 기존 `Tier` 필드 재사용이라 데이터 추가 없이 임계값 하나로 제어.
  - 기각한 대안: 카테고리 하드코딩 / 신규 "경매 가능" 태그 — 티어 필드로 충분하고 데이터
    편집 비용이 낮음. (태그 방식은 미래에 예외(특정 저티어 희귀품)가 필요해지면 재론.)

- **[결정] 매물 1개 ↔ 제안 다수(번들).** 경매에 내놓는 매물은 **항상 아이템 1개**, 거기에
  대응해 올리는 제안은 **여러 아이템 묶음(번들) 허용**. 양방향 동일(플레이어가 살 때 여러
  개로 제안 / 플레이어가 판 매물에 시뮬 구매자가 여러 개로 제안).
  - 이유: 사용자 선택. 매물은 단순하게 유지하되, 물물교환에서 가치를 맞추기 쉽게 대응 측만
    번들 허용.
  - 함의: 성사 판정은 **제안 묶음의 True 합** vs 매물 True × 수락 임계. 번들은 감정가 밴드
    오차가 누적돼 사기 깊이를 키운다(겉보기 합계 ≠ True 합계).
  - 기각한 대안: 완전 1:1 — 딱 맞는 짝이 드물어 거래가 자주 무산. 양쪽 다 번들 — 매물까지
    묶으면 UI·매칭이 과해짐.

### 2. 구조 의도 (경계를 왜 여기 그었는가)

- **월드 소유 + 마을 접근**을 분리한다. 시장 *상태*는 월드에 하나(신규 `AuctionManager` +
  `WorldData`의 신규 필드), 시장 *입구*는 마을 건물의 서비스 비트(`ProvidedService`)다. 이렇게
  나눠야 "여러 마을에서 하나의 시장"이 자동 성립하고, 미래에 진짜 온라인으로 바꿀 때
  **상태 소유자만 서버로 교체**하면 되며 접근/UI 계층은 그대로 남는다.
- **가치 계산은 순수 함수로 격리**한다(§3, `ItemTradeValuation`). 상태·수명주기가 없는 순수
  로직이므로 static이 정당(CLAUDE.md 로직 배치 규칙 4). 시장·상인·감정 UI가 공유한다.
- **시장 콘텐츠(매물·제안) 생성은 결정론적 롤러**로 격리한다(§5, `AuctionListingRoller`).
  기존 `VillageTradeStockRoller`가 선례: `UnityEngine.Random` 금지, `DerivedSeed`+`HistoryRng`로
  (seed, cycle, slot)에서 재현. save/load·되감기 후에도 같은 매물이 나와야 하기 때문.
- **가변 상태(매물·제안·에스크로·사이클)는 매니저+세이브 데이터가 소유**한다. static 금지
  (CLAUDE.md 로직 배치 규칙 1·가드레일: 캐시·풀은 수명주기 있는 소유자 필요).
- **True Value ↔ Estimated Value 분리가 사기 메커니즘의 축이다.** 상대(시뮬 판매자/구매자)는
  True Value로 판단하고, 플레이어 UI는 Estimated Value(오차 포함)만 본다. 이 비대칭이 사기와
  득템을 동시에 만든다.

### 3. 아이템 가치 모델 (핵심)

두 개의 값이 존재한다:

**(a) True Value — 내부 실가치 (플레이어에게 직접 노출 안 함)**
순수 함수 `ItemTradeValuation.GetTrueValue(ItemData) → int`. 상태 없음, 테이블만 참조.
- 베이스: `ItemTable.BasePrice` (0이면 경매 불가로 취급).
- 티어 가중: `ItemTable.Tier`가 높을수록 가치 상승(특별 아이템일수록 가파르게).
- **장비**: `EquipmentData.Mods` 기여 합산이 실가치를 지배한다.
  - Base/Implicit 모드: 아이템 정체성 → 베이스 기여.
  - Prefix/Postfix 모드: **모드의 `Tier`가 높을수록, 붙은 개수가 많을수록** 가파르게 가치
    상승(같은 BasePrice라도 6모드 T1 아이템 ≫ 2모드 저티어 아이템).
  - 품질(`EquipmentData.Quality`) 기여.
- **스킬북**: 스킬 희귀도/티어 + 소켓된 페이지(`SocketedPages`) 가치 합산.
- **스킬페이지**: 참조하는 `SkillEffect`의 티어.
- 계수(모드 티어별 가중치 등)는 **튜닝 대상**(열린 질문). 최초엔 단순 가중표로 시작.

**(b) Estimated Value — 플레이어가 보는 감정가 (항상 오차 밴드)**
`GetEstimatedValue(ItemData) → (low, high)`.
- True Value에 **결정론적 오차**를 씌운 밴드로만 노출한다(정확 실가치는 절대 노출 안 함).
  오차 크기 e는 아이템 티어·유형과 시뮬 판매자의 은폐 성향(§5)으로 결정된다. **밴드를 좁히는
  감정 완화 기능은 없음**(도입 안 함, 미래 유보).
- **결정론 필수**: 매 프레임 흔들리면 안 됨. 오차 시드 = `ItemData.ItemInstanceId`(시장 매물은
  +listingId)로 고정 → 같은 아이템은 항상 같은 밴드.
- 표시: 범위 밴드("대략 800~1200") 형태.

**사기 성립 구조**: 플레이어는 밴드만 보고 거래를 수락하지만, 실제 손익은 True로 결정된다.
True 1000짜리를 내주고 True 600을 받으면 손해(사기). 반대면 득템. 밴드(오차)가 넓을수록
도박성이 커진다. 리스크 완화 수단(감정)은 두지 않으므로 눈썰미·경험이 곧 실력이다.

### 4. 거래 흐름 (직접 제안 모델, 시뮬레이션)

시뮬 시장이므로 플레이어가 **구매자일 때**와 **판매자일 때** 두 방향을 모두 지원한다.

**A. 플레이어가 매물을 획득 (플레이어=구매자)**
1. 시뮬 판매자가 공유 풀에 매물을 올려둠(각 매물은 숨은 True Value + 판매자 수락 성향 보유).
2. 플레이어가 매물 열람 — 아이템 + **감정가**만 보임(실가치 아님).
3. 플레이어가 자기 인벤토리 아이템(1개 또는 번들)을 **제안**.
4. 시뮬 판매자가 제안의 True Value를 자신의 수락 임계와 비교해 **즉시 수락/거절**.
   공정한 판매자는 ≈100% 이상이면 수락, 탐욕형은 더 요구, 순진형은 밑지고도 수락(→ 득템 기회).
5. 수락 시 아이템 스왑. 거절 시 제안 반환.

**B. 플레이어가 매물을 등록 (플레이어=판매자)**
1. 플레이어가 특별 아이템 **1개**를 공유 풀에 **등록**(아이템은 에스크로로 이동, §7).
2. 게임 시간이 흐르면 시뮬 구매자가 **제안(1개 또는 번들)을 생성**해 붙임. 일부는 공정, 일부는
   **겉만 번드르르한 미끼**(감정가는 높아 보이나 True Value는 낮음 → 사기 미끼).
3. 플레이어가 들어온 제안들(제안 아이템의 감정가 표시)을 보고 **수락/거절**.
4. 수락 시 스왑. 미판매 매물은 N 게임시간 후 만료 → 아이템 반환.

이 구조로 사기가 양방향으로 성립: 살 때 과지불, 팔 때 나쁜 제안 수락.

### 5. 시뮬레이션 시장 채우기

- 공유 풀은 항상 K개 매물 유지. **마켓 사이클**(예: 게임 하루 또는 N시간)마다 만료 매물 제거
  + 신규 매물 결정론 롤인. 선례: `VillageTradeStockRoller.GetRestockCycle`/`RollStockPlan`.
- 매물 아이템 생성: 자격 티어로 필터한 아이템 테이블에서 뽑고, 장비는 결정론적으로 모드를
  롤(기존 아이템 생성 경로 재사용). 각 매물에 True Value 부여.
- **판매자 성향(공정/탐욕/순진)**이 수락 임계와 감정가–실가치 격차(은폐 성향)를 결정 →
  사기와 흥정의 원천. 성향 분포는 튜닝(열린 질문).
- 플레이어 매물에 붙는 제안도 (listingId, offerCycle)에서 결정론 생성 → save/load 안전.

### 6. 저장 / 에스크로

- `WorldData`에 신규 필드 `AuctionMarket`(신규 `AuctionMarketSaveData`) 추가. `Chronicle`·
  `WorldSim`·`VillageDatas`와 같은 방식으로 `DataManager.Save()/Load()`에 배선.
- 세이브 데이터 내용: 현재 매물 풀, 마켓 사이클/에폭, 플레이어 매물에 붙은 대기 제안, 시드,
  **에스크로 아이템**.
- **에스크로**: 플레이어가 등록한 아이템은 인벤토리에서 빠져 시장 세이브 데이터가 보관(판매/
  만료/취소까지). 복제·유실 방지. 이건 코드로 복구 불가한 필수 계약.

### 7. 접근 · UI

- 신규 서비스 비트 `ProvidedService.AuctionHouse` + 신규 `BuildableItemTable` 행(경매장 건물).
  마을에 이 건물이 있으면 F키로 열림 — 상태는 월드 공유라 어느 마을에서 열든 같은 풀.
- 신규 `UIAuctionHouse` — 탭 2개: **둘러보기(구매)** / **내 매물(판매 + 들어온 제안)**.
  라우팅·F키 프롬프트는 기존 `UIShopMerchant` 경로를 그대로 따른다.

### 8. 제약 · 전제

- `UnityEngine.Random` 금지 — 모든 매물/제안/감정 오차는 결정론(save/load·되감기 불변).
  기존 `DerivedSeed`+`HistoryRng` 채널 재사용.
- 물리 NPC 수·직업을 시장 입력으로 쓰지 않는다(마을 도메인 경계와 동일 원칙). 시뮬 판매자/
  구매자는 순수 가상 개체이지 실제 NPC 엔티티가 아니다.
- 감정 완화 기능이 없으므로 골드는 교환·감정 어디에도 개입하지 않는다. 등록비/성사 수수료를
  골드 싱크로 둘지는 열린 질문(§9). 골드는 이미 전역(`PlayerData.Gold`).

### 9. 열린 질문

- [ ] **가치 공식 계수**: 모드 티어별 가중, 티어 곡선, 품질 기여 — 튜닝 패스 필요.
- [ ] **감정가 밴드 폭(오차 e) 튜닝**: 티어·유형·판매자 은폐 성향별로 밴드를 얼마나 넓힐지.
- [ ] **마켓 파라미터**: 사이클 길이, 풀 크기 K, 플레이어 매물당 제안 수/주기, `AuctionMinTier`.
- [ ] **판매자/구매자 성향 분포**(공정/탐욕/순진 비율)와 사기 미끼 등장 빈도.
- [ ] **수수료/등록비**: 골드 싱크로 등록비·성사 수수료를 둘지.
- [ ] **마켓 사이클 구동 위치**: 신규 `System_AuctionMarket`(게임시계 기반 대주기) vs
      `HistoryManager` 시간 전진 훅. 우선순위 밴드도 함께 결정.

## 구현 계획 (2026-07-23 기준 — 완료 시 이 블록 전체 삭제)

> 아직 GO 신호 없음. 아래는 착수 시 붙을 지점을 개념→심볼로 남긴 **코드 앵커 지도**다.
> (라인 번호가 아니라 안정적 심볼로만.)

### 코드 앵커 (이 기능이 기존 코드에 붙는 지점)

- **월드 세이브 소유자** — `WorldData`에 `AuctionMarket` 필드 추가 → `DataManager.Save()/Load()`가
  `Chronicle`/`WorldSim`/`VillageDatas`를 배선하는 방식과 동일하게 연결.
- **매니저 등록** — `AR.s.Village`(=`VillageManager`) 선례를 따라 `AR.s.Auction`(=신규
  `AuctionManager`) 접근자 추가. Save/Load는 `VillageManager.Save()/Load(...)` 패턴 미러.
- **가치 계산(신규 static)** — `ItemTradeValuation`(True/Estimated). 입력: `ItemData` +
  `ItemTable`/모드 테이블. 사기 오차는 `ItemData.ItemInstanceId` 시드.
- **결정론 롤러(신규 static)** — `AuctionListingRoller`. 선례: `VillageTradeStockRoller`
  (`RollStockPlan`/`GetRestockCycle`), 시드 채널은 `DerivedSeed`+`HistoryRng`.
- **거래 API(신규, 매니저 메서드)** — 선례: `VillageManager.BuyItemFromMerchant` /
  `SellItemToMerchant`. 인벤토리 이동은 `Inventory`/`ItemManager`.
- **건물·서비스** — `ProvidedService` enum에 `AuctionHouse` 추가; 신규 `BuildableItemTable` 행;
  F키 라우팅은 `ServiceUIRouter`; 프롬프트/근접 집계는 `System_VillageServiceProximity` /
  `System_VillageInteractionPrompt`.
- **UI** — 신규 `UIAuctionHouse`, 선례 `UIShopMerchant`.
- **매물 아이템 생성** — 장비 생성/모드 롤 경로(`EquipmentData.InitBaseMods/InitImplicitMods` +
  affix 롤러) 및 `ItemManager.CreateInventoryItemData` 재사용.
- **자격 판별** — `ItemTable.Tier` ≥ `AuctionMinTier`.
- **마켓 사이클 구동** — 신규 `System_AuctionMarket`(대주기) 또는 `HistoryManager` 시간 전진 훅
  (열린 질문에서 확정 후).

### 작업 순서 (열린 질문 확정 후 착수)

- [ ] 세이브 스캐폴딩: `AuctionMarketSaveData` + `WorldData.AuctionMarket` + `DataManager` 배선 +
